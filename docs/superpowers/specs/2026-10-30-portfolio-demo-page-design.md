# AI-Ad-QA 本地作品集演示页设计（待确认）

## 目标与边界

给作品集演示者一个可上传广告视频、图片或输入脚本的本地页面。页面调用已发布的 Dify 多模态工作流，只呈现可读 Markdown 报告、运行状态与必要错误信息；不显示 `evaluation_result`、`technical_details`、`state_json`。保留现有 Dify 工作流和 FastAPI 视频处理服务，不改它们的 API 契约。

第一版只在本机运行，不做公网部署、账号系统、历史记录或结果数据库。`localhost` 不能当成可供外部访问的作品集链接；对外展示仍以 GitHub 仓库、截图或录屏为主。

## 入口与文件约定

- 新增 `demo/`：独立的本地演示服务和静态页面，不放 Dify DSL 或运行时上传文件。
- 新增 `启动演示页.cmd` 与对应 PowerShell 脚本：使用项目 `.venv`，绑定 `127.0.0.1:8001`；进程结束后临时配置消失。
- 先在项目根 `CLAUDE.md` 定义 `demo/` 的目录职责、端口、凭据与验证规则，再创建实现文件。
- 更新根 README、`workflow/README.md` 与演示页说明，区分 Dify 原生分享页和干净的本地演示页。

## 数据流

1. 用户在 `http://127.0.0.1:8001` 选择 `video`、`image` 或 `script`，填写产品、受众、转化目标；视频或图片选择文件。
2. 浏览器将表单提交给同源 `demo` 服务。服务端按类型、扩展名和大小上限校验；只接受一个素材，不把原文件写入仓库或长期存储。
3. 服务端使用进程环境变量中的 `DIFY_DEMO_API_KEY` 调用本机 Dify Service API。文件先上传至 Dify，再将返回的文件 ID 作为工作流文件输入；脚本直接作为文本输入。Dify API 的具体字段以本机应用“访问 API”页核对。
4. 服务端等待工作流结束，只把 `report_markdown`、`final_status` 和简短的执行错误返回浏览器；其他输出不下发给展示页。
5. 浏览器用 `textContent` 和受限的标题、列表解析展示 Markdown，避免把模型文本当作 HTML 执行。运行时显示进度和耗时；失败时给出可操作的中文错误。

## 凭据与网络

- API Key 由用户在 Dify 中创建并在启动演示服务的进程环境中设置。代码、Git、页面源代码、浏览器请求和日志均不得出现密钥值；本次不改 `.env`。
- 演示服务只绑定 `127.0.0.1`，不启用 CORS，也不接收用户传入的任意 Dify URL，防止开放代理或局域网滥用。
- Dify 地址固定为本机 `http://localhost:18080/v1`，可通过非敏感进程环境变量覆盖，用于本机端口差异。
- 不把第三方上传文件写入项目目录；Dify 自身保留策略沿用现有部署配置。

## 验证

- 测试文件类型/大小限制、三种输入映射、Dify 上传与运行响应解析、密钥缺失、超时和错误响应；使用模拟 Dify 响应，不在自动化测试中消耗模型额度。
- 在用户自行设置密钥后，用现有合成 MP4、测试图片和短脚本各做一次本地演示页真实运行；只声称实际完成的分支。
- 运行项目完整单元测试，检查页面不含技术 JSON 和密钥，再实际打开页面核对布局、输入切换和报告可读性。

## 风险与后续

- Dify API Key 目前未配置到本演示服务，真实联调必须由用户在本机 Dify 创建或提供到进程环境；不得从数据库或浏览器会话提取。
- 视频工作流约 50 秒，演示页需要明确等待状态和足够的请求超时；若本机 API 的 blocking 模式有更短限制，改用 Dify 的流式完成事件。
- 如未来要让别人直接打开网页，需要单独设计部署、访问控制、额度限制、文件留存和模型费用；不属于本地第一版。
